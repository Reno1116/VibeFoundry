# CLAUDE.md

## 仓库定位

VibeFoundry 是用于设计和开发工作效率工具的个人仓库。每个工具只走两个阶段：先确认需求并在 Figma 完成交互，再实现代码并持续调优。

## 两步工作流

### 1. 需求与交互

目标是先把"做什么"确认清楚，不在这一阶段写正式代码。

1. 从 `工具设计模板.md` 复制一份到 `projects/<工具名>/design.md`
2. 与用户确认目标、用户、核心流程、范围和成功标准
3. 用户在 Figma 输出关键页面、状态和交互
4. 人工确认需求和 Figma 交互后，将文档状态改为 `已确认`

唯一交付物：`projects/<工具名>/design.md`

### 2. 开发与调优

以已确认的 `design.md` 和 Figma 为准，在同一项目目录内完成代码、测试和迭代。

1. 建立最小可运行版本，先打通核心流程
2. 对照 Figma 实现界面和交互
3. 运行真实场景验证，修复问题并调优体验
4. 在项目 `README.md` 记录启动方式、当前能力和已知问题

需求或交互发生实质变化时，先回到第一步更新 `design.md` 和 Figma，再继续开发。

## 目录结构

```text
VibeFoundry/
├── README.md
├── 工具设计模板.md
├── projects/
│   └── <工具名>/
│       ├── README.md       # 启动方式、当前能力、已知问题
│       ├── design.md       # 已确认需求与 Figma 交互链接
│       ├── src/            # 代码；按技术栈调整
│       └── tests/          # 测试；需要时创建
```

一个工具的资料和代码始终放在同一个 `projects/<工具名>/` 下。

## 基本约定

- 中文文档统一使用 UTF-8 和 LF
- 项目目录使用简短的英文小写名称，例如 `file-organizer`
- 不提前创建用不到的目录；技术栈需要什么再创建什么
- Figma 不追求完整视觉稿，但必须覆盖核心流程、空状态、加载状态和失败状态
- 未经确认的设计不进入开发；小型修复可直接在第二步内完成
- 不主动创建 `src/` 或 `tests/` 空目录 — 只在有实际代码时创建

## Git 提交

完整的提交规范见 [.claude/提交规范.md](.claude/提交规范.md)。

提交标题格式：

```text
[阶段][动作](工具名) 具体结果
```

示例：

```text
[design][新增](jenkins-launcher) 新增需求与交互设计
[dev][新增](jenkins-launcher) 完成 API 请求模块
[dev][修复](file-organizer) 修复批量重命名中文乱码
[repo][整理] 简化仓库结构
```

**Agent 提交前必须获得用户同意。** 一次提交只做一件事；正文写清楚改动内容、验证方式、后续事项。

## 技术偏好

- 平台：Windows 为主
- 技术栈不做统一限制，按工具需求选择（Python、Node.js 均可）
- 凭据类信息不写入仓库、日志或配置文件（使用系统凭据管理器）
